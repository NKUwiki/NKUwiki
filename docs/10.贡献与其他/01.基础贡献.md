### 文章结构

文章由两部分组成

1. Frontmatter
2. 正文

### Frontmatter

Frontmatter 是文章的一些基本信息，必须在 Markdown 文件的**顶部**，并且被包裹在一对三短划线中间。示例：

```
---
title: 基础贡献
description: 向NKUwiki投稿的基础指南：Markdown写作规范、文章Frontmatter字段、标题图片表格等语法，以及内容提交方式。
date: 2026-09-10
lastUpdated: 2026-09-14
author:
  - name: Cure
categories:
  - 贡献
    - 测试
tags:
  - 基础贡献
  - 测试
permalink: /pages/BasicContribution/
---
```

此 Wiki 常用 Frontmatter 内容即为以上内容

- **title** 会在正文开头生成一个**1 级标题**，会**覆盖**掉手动写的一级标题，所以你可以不单独写 1 级标题
- **description** 该文章的简介
- **date** 为文章创建日期，格式为 YYYY-MM-DD，后续修改时保留。
- **lastUpdated** 为最近一次内容更新日期，格式为 YYYY-MM-DD。新增、删除或修正正文信息、文字勘误、措辞修改，以及补充或修复有效资料链接时，在同一个提交中手动更新此字段；修改文章引用的脑图或组件中的实际内容时也需同步更新。纯排版、分类、SEO 元数据、文件迁移和等价的组件替换不更新日期。
- 新文章只填 date；有后续内容更新时再添加 lastUpdated。未填写时不显示页尾更新时间，也不进入“最近更新”列表。构建时不会从 Git 自动生成日期，普通目录和归档仍可按创建日期展示文章。
- **author** 文章作者，可不写：页尾的作者胶囊只按这里列出的作者展示，不写则显示默认的`NKUwiki-Group`。写法见下节「作者与头像」。
- **categories** 即为文章分类，可以多次缩进表示嵌套（子目录）
- **tags** 即为标签
- 短横线“-”，使用 tab 缩进。
- 一般情况下 categories 和`.md`文件所在目录相对应，具体可参考同目录文件的写法。
- **permalink** 可以不写，会自动生成链接。但是建议写，以固定文章链接
- **order** 可以不写，用来控制排列顺序，数字越小越靠前，详见下面的「排列顺序（order）」小节。

更多内容请查看<https://vitepress.dev/zh/guide/frontmatter>

### 排列顺序（order）

`order` 是一个可选的数字字段，**数字越小越靠前**。它同时作用于**左侧边栏**和**专题页**（`/categories/`），两处保持一致。

**文章排序**：在文章的 frontmatter 里直接写。

```yaml
---
title: 新生报到须知
categories:
  - 新生入学
order: 1
---
```

**分类（目录）排序**：一般不用单独写，分类会跟着里面的文章走——取该目录下所有文章（含更深层子目录）`order` 的**最小值**。想强行指定某个分类的位置，就在该目录里放一个 `index.md`（目录还没有概览页就新建一个），在它的 frontmatter 里写 `order`：

```yaml
---
title: 新生入学
order: 1
---
```

这个 `index.md` 同时就是该分类的概览页，会作为一条文章出现在侧边栏的这个分类下（其余字段按普通文章照常写即可）。

**规则细则**

| 情况 | 结果 |
| --- | --- |
| 写了 `order` | 按数字升序排在前面，如 `1`、`2`、`10` |
| 没写 `order` | 统一排在**所有**写了 `order` 的条目后面 |
| 都没写 / 数字相同 | 保持原来的顺序（文件名、目录名） |
| 全站都不写 | 排序结果与完全不用这个功能时一致 |

所以不需要给每篇都写：只给想提前或想固定的少数几篇写 `order` 即可，其余文章维持原样。数字可以跳着写（`10`、`20`、`30`），方便以后往中间插新文章。

::: tip
`order` 只影响展示顺序，不影响网址（permalink）、分类归属和搜索结果。
:::

### 作者与头像

#### 作者从哪里来

文章页尾的作者胶囊（头像 + 名字）只取 frontmatter 的 `author` 字段，按声明顺序列出；
GitHub、头像、联系方式等其余信息按名字到 `docs/.vitepress/members.ts` 的成员表里查。

#### author 的写法

**推荐只写名字**（成员表里已有的成员），多个作者就写多个元素：

```
author: [Cure, NKUwiki-Group]
```

不在成员表里的客串作者用对象写法就地补字段，写了的会覆盖成员表里的同名信息：

```
author:
  - name: Cure
  - name: 客串作者
    github: someones
    avatar: https://example.com/avatar.png
    link: https://blog.example.com
    contact: QQ：123456789
    email: guest@example.com
```

每个元素的字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| name | 是 | 显示的名字；缺了这一条会被忽略。其余信息按这个名字到成员表里查 |
| github | 否 | GitHub 用户名，用于拉取头像（`github.com/<用户名>.png`）和默认跳转的个人页 |
| avatar | 否 | 头像图片地址，例如 `https://example.com/avatar.png`；优先级最高 |
| link | 否 | 点击作者胶囊时打开的链接；不填默认跳 GitHub 个人页，没有 GitHub 就不可点击 |
| contact | 否 | 悬停作者胶囊时展示的联系方式标签（纯文本）；不填时回退显示 GitHub 用户名、邮箱 |
| email | 否 | 联系邮箱，contact 的兜底之一；写 `a@b.com` 或 `mailto:a@b.com` 都行 |

悬停标签的取值顺序：`contact` → GitHub 用户名 → 邮箱，取第一个有值的；全都没有时悬停不弹。

新增成员或修改成员信息，编辑 `docs/.vitepress/members.ts` 的 `members` 表即可，文章不用动。

#### 写法约束

- 必须是数组：`author: Cure`、`author: { name: Cure }`（单个对象）会被忽略；数组元素可以是名字字符串或对象，二者可混用。
- 键名是 `author`（单数）。页面数据里的 `authors` 是构建时生成的内部字段，写在 md 里无效。
- 名字本身带空格没问题，会整体当作一个名字。
- 如下写法会被忽略：`author:` 空值、字符串、数字、嵌套数组，以及没有 `name` 的元素。
- 名字或链接里有 `: `、`#`，或开头是 `@`、`?`、`&`、`*` 这类 YAML 特殊字符时，用引号包起来，例如 `link: "mailto:a@b.com"`。

#### 头像与兜底

- 页尾顺序：完全按 frontmatter 里声明的顺序，不做自动排序或去重；同一个人写两次就会出现两条。
- 头像推导顺序：显式 `avatar` 链接（frontmatter > 成员表）→ GitHub 头像 → 姓名首字生成的本地头像；头像加载失败时也会回退到首字头像。
- 首字头像由姓名生成（首字 + 由姓名决定的稳定色相），不请求任何外部头像服务，离线时也能显示。
- 悬停作者胶囊会显示联系方式标签（`contact` → GitHub 用户名 → 邮箱，取第一个有值的）；点击胶囊打开 `link`（不填默认 GitHub 个人页），没有可跳的链接时胶囊不可点击。
- 没写 `author` 时页尾显示组织账号 `NKUwiki-Group`（成员表里配置，GitHub 头像）。
